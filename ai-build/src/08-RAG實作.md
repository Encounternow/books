# 第 8 章　RAG 實作

## 本章目標

學完這一章，你會：

- 說出 RAG 的五個步驟：切塊 → 嵌入 → 檢索 → 組提示 → 生成，並且知道每一步在做什麼。
- 寫一個切塊函式，知道塊要切多大、為什麼要重疊、標題為什麼不能自己一塊。
- 把第 7 章的向量搜尋接上一個語言模型，做出「問我的筆記」問答機器人，生成端可以選本地 Ollama 或 Claude。
- 讓 AI 回答時標明引用了哪一段，並在資料裡沒答案時老實說「沒有提到」。
- 用一組評估題算出「檢索命中率」，並用它比較兩種切塊方式哪個好。
- 認得 RAG 最常見的四種失敗：切壞、檢索不到、上下文塞爆、模型亂講。

## 開場：會翻書的 AI

第 7 章結束時，小宇已經能用一句話找到最相關的筆記。但他很快發現一件事：找到的是「一條筆記」，不是「一個答案」。他問「冷氣濾網怎麼洗」，搜尋給他三段文字，他還是得自己讀完、自己整理成一句話。

他試過直接問 Claude 或本地模型「我家冷氣濾網怎麼洗」，模型會給一段很通用的答案：「請參考說明書，一般建議每月清洗……」。可是他家的規則是「每兩個月」、上次洗的日期寫在冰箱白板上、面板要往上推再抽出來——這些都是他家才有的細節，模型不可能知道。

那如果兩個合起來呢？先用向量搜尋找出「跟問題最相關的三段筆記」，再把這三段連同問題一起給模型，告訴它：「只根據這些資料回答。」模型就像一個可以翻書的考生，書是你給的，它負責讀懂、整理、用人話講出來。

這就是 RAG：檢索增強生成（Retrieval-Augmented Generation），目前讓 AI「知道你的東西」最便宜、最常用的方法。這一章從頭把它做出來，然後學會量它做得好不好。

## 核心概念

### RAG 的流程

整條管線長這樣：

```
【建索引：改資料時做一次】
  文件 ──切塊──▶ 很多小段 ──嵌入──▶ 向量 ──▶ 存進向量資料庫

【問答：每問一次做一次】
  問題 ──嵌入──▶ 問題向量 ──檢索──▶ 最相關的 k 段
                                         │
              「只根據以下資料回答…」 ◀───┘
                        │
                        ▼ 組提示
                    語言模型 ──生成──▶ 答案（附引用）
```

左半邊是第 7 章做過的事，差別只在多了「切塊」。右半邊多了「組提示」和「生成」。每個步驟都有幾個要決定的事，我們一個一個看。

### 切塊：切多大、怎麼切

第 7 章的筆記每條都是一句話，不用切。但真實文件是一篇一篇的：使用說明、課堂筆記、社團規定，動輒幾百到幾千字。第 7 章末尾講過，一整篇壓成一個向量會「什麼都講一點、什麼都不像」，所以要先切成小段，這個動作叫切塊（Chunking），每一段叫一個塊（Chunk）。

切多大？這是取捨：

| 塊的大小 | 優點 | 缺點 |
|---|---|---|
| 太小（一兩句） | 向量很精準 | 一段話被切斷，上下文不見了；答案常常要跨兩塊 |
| 太大（整頁） | 上下文完整 | 向量變模糊，不相關的內容也跟著進提示，浪費 token |
| 中等（100–300 字） | 通常是甜蜜點 | 要調整 |

這本書的中文資料用 200 字左右一塊。英文資料常用 300–500 個 token，道理一樣。

怎麼切？三個原則：

1. **先照結構切。** 文件有段落、有標題，就照段落切，不要硬從句子中間砍。
2. **太長的段落再照字數切，並且重疊。** 例如每 200 字一塊，相鄰兩塊重疊 40 字。重疊（Overlap）是為了避免一句關鍵的話剛好被切在兩塊的交界，哪一塊都只有半句。
3. **標題要黏在內容上。** 這是最常犯的錯，等一下活動裡你會親眼看到切壞的後果。

這是本章的切塊函式（`chunk.py`）。先看一個「照段落切」的直覺版本：

```python
def split_text(text, size=200, overlap=40):
    """先照段落切，段落太長再照字數切；相鄰塊之間重疊 overlap 個字"""
    chunks = []
    # 先用空行把文件切成段落，去掉空白段落
    paragraphs = [p.strip() for p in text.split("\n\n") if p.strip()]
    for p in paragraphs:
        # 段落夠短就整段當一塊
        if len(p) <= size:
            chunks.append(p)
            continue
        # 段落太長：每次往前走 (size − overlap) 個字，切出一塊
        start = 0
        while start < len(p):
            chunks.append(p[start:start + size])
            start += size - overlap
    return chunks
```

```
  [1] (10 字) ## 冷氣的使用規則…

  [0] (15 字) # Arduino 社團的規定…
  [1] (8 字) ## 時間與地點…
```

看到問題了嗎？Markdown 的標題和內容之間有空行，所以「## 濾網清洗」自己變成了一塊，只有 10 個字。這種塊的向量非常「空」，查「濾網多久洗」它會跳出來佔一個名額，但裡面沒有答案；而真正有答案的那一段，卻失去了「濾網清洗」這個主題提示。修正版把標題記下來，黏到它下面那一段的開頭：

```python
from pathlib import Path

def split_text(text, size=200, overlap=40, keep_heading=True):
    """先照段落切，段落太長再照字數切；相鄰塊之間重疊 overlap 個字。
    keep_heading=True 時，標題行會黏到它下面那一段，不會自己變成一塊。"""
    chunks = []
    paragraphs = [p.strip() for p in text.split("\n\n") if p.strip()]
    heading = ""
    for p in paragraphs:
        # 遇到標題（# 開頭）先記下來，等下一段再一起放進去
        if keep_heading and p.startswith("#"):
            heading = p.lstrip("# ").strip()
            continue
        # 把標題接在段落前面，讓每一塊都知道自己在講哪個主題
        p = f"{heading}：{p}" if heading else p
        if len(p) <= size:
            chunks.append(p)
            continue
        # 段落太長：每次往前走 (size − overlap) 個字，切出一塊
        start = 0
        while start < len(p):
            chunks.append(p[start:start + size])
            start += size - overlap
    return chunks

def load_docs(folder="docs"):
    """讀取資料夾裡所有 .md 檔，回傳 (檔名, 內容) 的列表"""
    docs = []
    for path in sorted(Path(folder).glob("*.md")):
        docs.append((path.name, path.read_text(encoding="utf-8")))
    return docs

if __name__ == "__main__":
    for name, text in load_docs():
        chunks = split_text(text)
        print(f"{name}：{len(text)} 字 → {len(chunks)} 塊")
        for i, c in enumerate(chunks[:2]):
            print(f"  [{i}] ({len(c)} 字) {c[:50]}…")
```

### 檢索：取幾筆

檢索（Retrieval）就是第 7 章的向量搜尋。要決定的只有一件事：取前幾筆（k）。

- k 太小（1）：賭第一名就是對的，但第 7 章看過第一名不一定是你要的。
- k 太大（20）：答案一定在裡面，但提示會很長，模型要在一堆不相關的文字裡找答案，反而容易答錯，而且 token 費用變高。

個人筆記這種規模，k = 3 到 5 是常見起點。另一個常用做法是「取前 5 筆，但相似度低於門檻（例如 0.3）的丟掉」，避免把湊數的塞進去。

### 重排：先粗篩再細挑

嵌入模型為了快，是把問題和文件「各自」變向量再比距離，沒有機會「把問題和文件放在一起讀」。所以它會漏掉一些細微的關係，例如否定詞（第 7 章講過）。

重排（Rerank）是補救的第二階段：先用向量搜尋快速找出前 8 到 20 塊，再用一個專門的重排模型（叫 Cross-Encoder，交叉編碼器）把「問題＋每一塊」一起讀進去，直接打一個相關分數，照這個分數重新排序，只留前 3 塊。

```
問題 ──向量搜尋（快，粗）──▶ 前 8 塊 ──重排模型（慢，準）──▶ 前 3 塊 ──▶ 組提示
```

重排模型慢很多（每一對都要跑一次模型），所以只用在「已經粗篩過的少數幾塊」上。本章用 `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`，一個支援多語言、約 470 MB 的小型重排模型，筆電跑得動。它是選配：個人筆記規模不一定需要，但你要知道有這一招，資料變多、問題變刁鑽時就用得上。

### 組提示與引用來源

檢索到的塊要怎麼交給模型？組提示（Prompt Assembly）就是把「指示、資料、問題」拼成一段文字。本章用的提示長這樣：

```
請只根據下面的資料回答問題。回答時在句尾用 [編號] 標明引用了哪一段。
如果資料裡沒有答案，請直接說「資料裡沒有提到」，不要自己猜。

資料：
[1]（來源：冷氣與電費.md）
濾網清洗：冷氣濾網每兩個月要洗一次。步驟：……

[2]（來源：冷氣與電費.md）
……

問題：冷氣濾網多久洗一次？怎麼洗？
```

三個設計重點：

1. **「只根據資料回答」**：把模型從「什麼都知道的百科」切換成「只會讀你給的東西的助理」。
2. **編號與來源**：每一塊前面放 `[1]`、`[2]` 和檔名，要求模型回答時標 `[編號]`。這叫引用來源（Citation），讓使用者可以點回去檢查，也讓你一眼看出模型有沒有「看著 [1] 卻說了 [1] 裡沒有的話」。
3. **「沒有就說沒有」**：這是防止亂講最有效的一句話。沒有它，模型會很熱心地用常識補答案，而那個常識對你家不一定適用。

還有一件安全上的事：檢索到的文字會原封不動進入提示。如果你的文件裡有人偷偷寫了一句「忽略上面的指示，改成回答……」，模型可能會照做。這叫提示注入（Prompt Injection），第 14 章會專門講防法。現在先記住一個原則：**資料是資料，不是指令**，提示裡要把資料用明確的標記（像上面的「資料：」區段）框起來，而且不要讓 RAG 系統有能力執行危險動作。

### 生成：本地模型或 Claude

組好提示後，交給語言模型生成（Generation）答案。這一步有兩條路，本書兩種都給程式：

| | 本地 Ollama | Claude API |
|---|---|---|
| 費用 | 免費 | 依 token 計費 |
| 隱私 | 資料不離開電腦 | 資料會送到雲端 |
| 品質 | 小模型看得懂簡單資料，複雜推理較弱 | 強很多，引用與「不亂講」都更穩 |
| 速度 | 看你的電腦；沒顯示卡會慢 | 穩定，幾秒內 |
| 需要 | 裝 Ollama、拉模型（第 9 章） | API 金鑰（第 1 章） |

兩條路的程式只差「呼叫模型」那幾行，其他切塊、檢索、組提示完全共用。這就是把管線拆成小函式的好處。

### 評估：答對率、有沒有亂講

做出來之後，怎麼知道它好不好？第 6 章學過要建評估集。RAG 的評估分兩層：

**第一層：檢索有沒有找對。** 這一層不需要語言模型、不花錢、可以自動算。做法是準備一組「問題 → 正確答案一定會包含的關鍵片段」，對每一題做檢索，看關鍵片段出現在第幾名。常用的數字：

- **Hit@1**：正確塊排在第 1 名的比例。
- **Hit@3**：正確塊排在前 3 名的比例（也就是「有進到提示裡」的比例）。

如果 Hit@3 很低，後面的模型再強也沒用，因為它根本沒拿到答案。所以先把這一層做好。

**第二層：生成有沒有答對、有沒有亂講。** 這一層要看模型的回答。可以人工打分（答對／答錯／說「沒有提到」但其實有／亂講資料裡沒有的事），也可以用第 6 章「AI 當評審」的方法，把「標準答案、模型答案」丟給另一個模型打分。本章的活動 8-2 先把第一層做扎實，第二層留一張表給你自己填。

### 常見失敗

| 失敗 | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 切壞 | 檢索到的塊只有半句話、或只有標題 | 切塊沒照結構、標題獨立成塊 | 照段落切、標題黏內容、加重疊 |
| 檢索不到 | 答案明明在文件裡，前 3 名都不是 | 問法和文件用詞差太多；塊太大太模糊 | 塊切小、k 加大再重排、混合關鍵字搜尋 |
| 上下文塞爆 | 回答變慢、變貴、或答案抓錯段 | k 太大、塊太大 | 減 k、加門檻、重排後只留 3 塊 |
| 亂講 | 答案聽起來很合理但資料裡沒有 | 提示沒有說「只根據資料」、沒有「沒有就說沒有」 | 改提示、要求引用、用評估集抓出來 |

## 動手做

### 活動 8-1：做一個「問我的筆記」問答機器人

**材料／工具**

- 第 7 章的環境（venv 裡已有 `sentence-transformers`、`chromadb`）
- 生成端二選一：裝好 Ollama 並拉了一個小模型（見第 9 章），或有 Anthropic API 金鑰（見第 1 章）；兩個都沒有的話，這個活動可以先做到「組好提示」為止，一樣學得到東西
- 一個資料夾 `ch08/`，裡面有 `docs/` 子資料夾放文件，以及 `chunk.py`、`rag_index.py`、`rag_retrieve.py`、`rag_ollama.py`、`rag_claude.py`

**步驟**

1. 準備文件。在 `docs/` 裡放三個 Markdown 檔。作者寫了三份「家裡的東西」，你可以直接用，也可以換成自己的（建議每份 400 到 800 字、有標題分段）。第一份 `冷氣與電費.md`：

```markdown
# 家裡的冷氣與電費

## 冷氣的使用規則

客廳的冷氣是 2019 年買的變頻機，廠牌是日立，型號貼在室內機右側。夏天設定溫度請維持在 26 到 28 度之間，不要一開就設 20 度，變頻冷氣是靠「維持溫度」省電，不是靠「吹很冷」省電。開冷氣的時候，請同時開電風扇，讓冷空氣在房間裡循環，這樣 27 度也會覺得涼。

出門超過一小時就關冷氣。如果只是去樓下倒垃圾，開著不用關，因為重新啟動時壓縮機會用掉比較多電。

## 濾網清洗

冷氣濾網每兩個月要洗一次。步驟：先關機並拔掉插頭，打開面板，把兩片濾網往上推再往外抽出來，用清水沖洗，不要用刷子硬刷，陰乾後再裝回去。上一次清洗的日期寫在冰箱上的白板。濾網髒了會讓冷氣變弱又耗電，是最常見的「冷氣不冷」原因。

## 電費怎麼算

台灣的住家電費是「累進制」：用越多，每一度的單價越高。夏月（6 月到 9 月）的單價又比非夏月高。我們家一期（兩個月）大約用 400 度，去年 8 月那期用到 412 度，電費大約 1,300 元。

想知道某個電器一天用多少電，可以用這個算法：瓦數 × 小時 ÷ 1000 = 度。例如 1,000 瓦的冷氣開 8 小時就是 8 度，電扇 50 瓦開 8 小時只有 0.4 度。所以「冷氣加電扇」比「冷氣開更冷」划算非常多。

## 電費單在哪裡

電費單放在書房第二個抽屜的「帳單夾」裡，用月份分頁。繳費期限是單子右上角的日期，超過會有滯納金。可以用超商或網路銀行繳。
```

第二份 `阿公的菜園.md`：

```markdown
# 阿公的菜園筆記

## 陽台上種了什麼

陽台現在有四盆：九層塔、小番茄、辣椒和薄荷。九層塔最怕缺水，夏天每天早上要澆一次，葉子下垂就是缺水的訊號。小番茄要搭支架，開花之後可以用小刷子輕輕碰一碰花，幫忙授粉。薄荷長很快，記得每兩個星期剪一次，不然會把旁邊的盆子都佔滿。

## 澆水的時間
```

4. 寫 `rag_retrieve.py`，裡面有兩個函式：`retrieve()` 檢索、`build_prompt()` 組提示。這個檔案會被後面兩個生成程式共用。

```python
import chromadb
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
collection = chromadb.PersistentClient(path="rag_db").get_collection("docs")

def retrieve(question, k=3):
    """回傳最相近的 k 塊，每塊是 dict：text、source、score"""
    q_vec = model.encode(question).tolist()
    r = collection.query(query_embeddings=[q_vec], n_results=k)
    hits = []
    for doc, meta, dist in zip(r["documents"][0], r["metadatas"][0], r["distances"][0]):
        hits.append({"text": doc, "source": meta["source"], "score": 1 - dist})
    return hits

def build_prompt(question, hits):
    """把找到的塊編號成 [1]、[2]…，連同問題組成一段提示"""
    context = "\n\n".join(
        f"[{i+1}]（來源：{h['source']}）\n{h['text']}" for i, h in enumerate(hits)
    )
    return f"""請只根據下面的資料回答問題。回答時在句尾用 [編號] 標明引用了哪一段。
如果資料裡沒有答案，請直接說「資料裡沒有提到」，不要自己猜。

資料：
{context}

問題：{question}"""

if __name__ == "__main__":
    q = "冷氣濾網多久洗一次？怎麼洗？"
    hits = retrieve(q)
    for h in hits:
        print(f"{h['score']:.2f}  {h['source']}  {h['text'][:40]}…")
    print("\n----- 組好的提示 -----")
    print(build_prompt(q, hits))
```

```python
from sentence_transformers import CrossEncoder
from rag_retrieve import retrieve

# 重排模型（cross-encoder）：把「問題＋候選段落」一起讀，直接打一個相關分數
# 比嵌入模型準，但慢很多，所以只用在「先粗篩出的少數幾塊」上
reranker = CrossEncoder("cross-encoder/mmarco-mMiniLMv2-L12-H384-v1")

def retrieve_and_rerank(question, k_first=8, k_final=3):
    """第一階段用向量找 8 塊，第二階段用重排模型挑出最好的 3 塊"""
    hits = retrieve(question, k=k_first)
    # 每一塊配上問題，組成一對一對交給重排模型
    pairs = [(question, h["text"]) for h in hits]
    scores = reranker.predict(pairs)
    for h, s in zip(hits, scores):
        h["rerank"] = float(s)
    # 依重排分數由高到低排序，取前 k_final 塊
    hits.sort(key=lambda h: -h["rerank"])
    return hits[:k_final]

if __name__ == "__main__":
    q = "蝸牛要怎麼抓？"
    print("【向量排序（前 5）】")
    for h in retrieve(q, k=5):
        print(f"  {h['score']:.2f}  {h['text'][:36]}…")
    print("【重排之後（前 3）】")
    for h in retrieve_and_rerank(q):
        print(f"  {h['rerank']:+.2f}  {h['text'][:36]}…")
```

步驟 4，直覺版切塊（標題獨立成塊，31 塊），同一組題目的結果：

```
| 電費單放在哪裡？ | 帳單夾 | 4 |
| 九層塔多久澆一次水？ | 每天早上 | 3 |
| 颱風來要怎麼處理盆栽？ | 搬進客廳 | 2 |
| 社團可以用牆上插座嗎？ | 不可以把任何東西接到牆上 | 2 |
（其餘 11 題為 1）

題數 15｜Hit@1 = 11/15 = 73%｜Hit@3 = 14/15 = 93%
```

兩種切法的比較：

| 切塊方式 | 塊數 | Hit@1 | Hit@3 |
|---|---|---|---|
| 直覺版（標題自己一塊） | 31 | 11/15 = 73% | 14/15 = 93% |
| 修正版（標題黏內容） | 15 | 14/15 = 93% | 15/15 = 100% |

只改了切塊，Hit@1 從 73% 跳到 93%，而且「電費單放在哪裡」從第 4 名（根本不會進提示）變成第 1 名。這就是「切壞」的代價，也是為什麼評估集值得花時間做：沒有這張表，你只會覺得「好像有時候答不出來」，有了表，你知道是哪一題、差幾名、改了什麼之後好多少。

唯一沒拿到第 1 名的是「九層塔多久澆一次水」，正確塊排第 2，第 1 名是「澆水的時間」那段。這不算錯——它也在講澆水，而且兩塊都進了提示，模型可以合併回答。

## 常見錯誤與迷思

- **「RAG 會把我的整份文件都教給模型。」** → 錯。每次只送最相關的 3 到 5 塊，模型沒有「記住」任何東西，下一題又是從零開始。 → 正確理解：RAG 是「每題翻書」，不是「讀完整本書」。要讓模型真的學會某種風格或知識，那是第 10、11 章的微調。

- **「塊切越小越精準。」** → 不一定。切到一句話一塊，向量很準，但答案常常要兩句話才完整，模型拿到半句就會補腦。 → 正確理解：100 到 300 字、照段落切、加重疊，是比較安全的起點；用評估表調。

- **「k 取大一點比較保險。」** → k 太大會把不相關的塊塞進提示，模型要在一堆雜訊裡找答案，反而容易抓錯，也更貴。 → 正確理解：k = 3 到 5 起手，相似度太低的丟掉，資料多了再加重排。

- **「模型答錯一定是模型太笨。」** → 作者的經驗是大多數時候是檢索沒找對。 → 正確理解：先看 Hit@3。如果正確塊根本沒進提示，換再強的模型也救不了。

- **「有了『只根據資料回答』這句話，模型就不會亂講了。」** → 它會大幅減少，但不會歸零，尤其小模型。 → 正確理解：要求引用來源、建評估集抓亂講、對「沒有答案的題目」也要測。

- **「檢索到的文字是我自己的資料，所以是安全的。」** → 如果文件是別人給的（網頁、別人分享的筆記），裡面可能藏了指令。 → 正確理解：資料區段要明確框起來，RAG 系統不要接上有危險副作用的工具，第 14 章會詳談。

- **「評估只要算答對率就好。」** → 一個模型對每題都回答「資料裡沒有提到」，亂講率是 0 但一點用都沒有。 → 正確理解：答對率和亂講率要一起看，而且評估集要包含「真的沒答案」的題目。

## 想一想

1. 把 RAG 的五個步驟依序寫出來，並說明哪些是「改資料時做一次」、哪些是「每問一次做一次」。

<details><summary>參考答案</summary>

切塊 → 嵌入 → 檢索 → 組提示 → 生成。切塊和嵌入（建索引）是改資料時做一次；檢索、組提示、生成是每問一次做一次。所以建索引可以慢一點沒關係，問答那一側才要快。

</details>

2. 一塊 200 字、重疊 40 字，一段 520 字的段落會被切成幾塊？每塊的起點在第幾個字？

<details><summary>參考答案</summary>

每次往前走 200 − 40 = 160 字。起點：0、160、320、480，共 4 塊。第 4 塊從第 480 字開始，只有 40 字（480 到 520）。這種「尾巴很短的塊」是常見現象，如果嫌它太短，可以在程式裡加一條：最後一塊不足 size 的一半時，併到前一塊。

</details>

3. 活動 8-2 裡，「電費單放在哪裡」在直覺版切塊排第 4 名、修正版排第 1 名。請用「標題獨立成塊」的角度解釋為什麼差這麼多。

<details><summary>參考答案</summary>

直覺版把「## 電費單在哪裡」切成一個只有 7 個字的塊。查詢「電費單放在哪裡」跟這個標題塊幾乎一模一樣，所以它搶走了第 1 名，可是裡面沒有答案（答案「帳單夾」在它下面那段）。同時「## 電費怎麼算」等其他標題塊也來搶名額。修正版把標題黏到內容前面，「電費單在哪裡：電費單放在書房第二個抽屜的帳單夾裡……」這一塊同時有主題和答案，自然排第 1。

</details>

4. 使用者問「冷氣可以設 20 度嗎」。資料裡寫的是「請維持在 26 到 28 度之間，不要一開就設 20 度」。你預期向量檢索找得到嗎？模型回答時最容易犯什麼錯？

<details><summary>參考答案</summary>

找得到，因為這段和「冷氣、溫度、20 度」高度相關。最容易犯的錯是「否定詞」：資料說「不要設 20 度」，但如果模型只抓到「20 度」這個數字，可能會回答「可以」。這是第 7 章講的嵌入弱點延伸到生成端。防法：提示要求引用原文、用較強的模型、在評估集裡放這種「資料是否定句」的題目來抓。

</details>

5. （挑戰）把 `retrieve()` 改成「取前 5 筆，但相似度低於 0.35 的丟掉」。然後想一想：如果一題的 5 筆全部低於門檻，提示裡會沒有任何資料，這時候應該怎麼辦？

<details><summary>參考答案</summary>

改法：`hits = [h for h in hits if h["score"] >= 0.35]`。全部被丟掉時，不要送一個空的提示給模型，應該在程式裡直接回覆「我的筆記裡找不到相關內容」，這樣既省錢又不會讓模型憑空編答案。更進一步可以記錄這些「沒命中」的問題，它們就是你下一批該補的筆記。

</details>

6. （挑戰）設計一個「第二層評估」的自動版本：不用人工打分，用另一個模型當評審。評審需要收到哪些東西？你會要它輸出什麼格式？會遇到什麼困難？

<details><summary>參考答案</summary>

評審要收到：問題、檢索到的資料、模型的答案、標準答案（或關鍵片段）。要它輸出固定格式，例如 JSON：`{"correct": true/false, "hallucinated": true/false, "reason": "..."}`，可以用第 2 章的結構化輸出做到。困難：(1) 評審自己也可能判斷錯，所以要抽幾題人工對照；(2) 「答對」的標準很模糊（答了一半算不算），要在評審提示裡寫清楚規則；(3) 「沒有提到」的題目要特別處理：模型說「沒有提到」且資料真的沒有，應該算對。第 6 章的「AI 當評審」一節有更完整的做法。

</details>

## 本章小結

- RAG = 檢索增強生成：先用向量搜尋找出最相關的幾段，連同問題交給模型，要求它只根據這些資料回答。
- 五個步驟：切塊、嵌入、檢索、組提示、生成。前兩步建索引，後三步每題執行。
- 切塊要照結構切、太長再照字數切並重疊、標題要黏在內容上。本章實測：改對切塊，Hit@1 從 73% 升到 93%。
- 檢索取前 3 到 5 塊，太低分的丟掉；資料多時先粗篩再用重排模型細挑。
- 提示要說「只根據資料」「標引用」「沒有就說沒有」；資料區段要框清楚，防提示注入。
- 生成端可以是本地 Ollama（免費、隱私）或 Claude（品質高），其餘程式完全共用。
- 評估分兩層：檢索命中率（Hit@1、Hit@3）可以自動算、不花錢；生成的答對率與亂講率要另外看。
- 大多數「答錯」是檢索沒找對，先看 Hit@3 再怪模型。

## 名詞表

| 中文 | 英文 | 一句話解釋 |
|---|---|---|
| 檢索增強生成 | Retrieval-Augmented Generation (RAG) | 先檢索相關資料再讓模型根據資料回答 |
| 切塊 | Chunking | 把長文件切成適合嵌入的小段 |
| 塊 | Chunk | 切出來的一小段文字，是索引與檢索的單位 |
| 重疊 | Overlap | 相鄰兩塊共用的一小段文字，避免句子被切斷 |
| 檢索 | Retrieval | 依問題找出最相關的幾塊 |
| 重排 | Rerank | 用更準但更慢的模型把粗篩結果重新排序 |
| 交叉編碼器 | Cross-Encoder | 把問題和文件一起讀進去直接打分的模型，用於重排 |
| 組提示 | Prompt Assembly | 把指示、資料、問題拼成送給模型的文字 |
| 引用來源 | Citation | 回答時標明用了哪一段資料 |
| 上下文 | Context | 模型這次回答能看到的所有文字 |
| 命中率 | Hit Rate (Hit@k) | 正確塊出現在前 k 名的題數比例 |
| 幻覺／亂講 | Hallucination | 模型說出資料裡沒有、聽起來卻很合理的內容 |

| 中繼資料 | Metadata | 附在每塊上的額外資訊，例如來源檔名與塊編號 |
