# 第 2 章　結構化輸出與工具使用

## 本章目標

學完這一章，你會：

- 說出為什麼「讓 AI 回一段話」不夠，程式需要的是固定格式的資料。
- 用 `output_config` 或 pydantic 類別讓模型回合法的 JSON，並直接變成 Python 物件。
- 解釋工具（tool）的概念：模型不會自己動手，它只會「要求」你的程式去做。
- 讀懂 `tool_use → 執行 → tool_result` 的迴圈，自己手寫一個，也會用 `tool_runner` 讓 SDK 自動跑。
- 知道並行工具呼叫是什麼，以及工具為什麼一定要驗證輸入。

## 開場：摘要工具的下一步

小安的三句摘要工具做好了，她想把每天的摘要存進試算表：一欄標題、一欄三句話、一欄關鍵字。她試著在 system prompt 裡寫「請用逗號隔開」，結果模型有時候多加一句「以下是摘要：」，有時候關鍵字用頓號不用逗號，程式一切字串就壞掉。她又想加「今天要不要帶傘」，但模型根本不知道今天的天氣，它只能編。

這兩個問題其實是同一件事的兩面。第一個問題是**輸出**：模型回的是自然語言，程式要的是結構。第二個問題是**輸入**：模型知道的只有訓練資料和你送進去的文字，它沒有手可以去查天氣、算數學、讀檔案。

這一章要給模型兩樣東西：一個固定格式的「表單」讓它填，以及幾隻「手」讓它用。這兩樣加起來，AI 就從「會講話的字典」變成「能做事的助理」。

## 核心概念

### 為什麼要結構化輸出

程式讀自然語言很痛苦：你要切字串、猜格式、處理各種例外。**結構化輸出（Structured Outputs）**反過來讓模型遷就程式：你先用 **JSON Schema** 畫好表單——有哪些欄位、每個欄位是字串、整數還是清單、哪些必填——API 保證回來的東西一定符合表單。

JSON（JavaScript Object Notation）你應該看過，就是 `{"name": "小安", "age": 14, "tags": ["理化", "程式"]}` 這種長相。Python 的 `json.loads()` 可以把它變成 dict。JSON Schema 則是「描述 JSON 長什麼樣」的 JSON：

```
{"type": "object",
 "properties": {"name": {"type": "string"}, "price": {"type": "integer"}},
 "required": ["name", "price"],
 "additionalProperties": false}
```

這段的意思是：回我一個物件，裡面有字串 `name` 和整數 `price`，兩個都必填，不要多給別的欄位。

### 用 output_config 回 JSON

把 schema 放進 `output_config={"format": {"type": "json_schema", "schema": ...}}`，模型回的第一個文字區塊就是合法 JSON：

```python
import json
import anthropic

client = anthropic.Anthropic()

# 用 JSON Schema 描述「我要的格式」：哪些欄位、什麼型別、哪些必填
schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "商品名稱"},
        "price": {"type": "integer", "description": "價格，新台幣整數"},
        "in_stock": {"type": "boolean"},
        "tags": {"type": "array", "items": {"type": "string"}},
    },
    "required": ["name", "price", "in_stock", "tags"],
    "additionalProperties": False,
}

# output_config.format 告訴 API：回覆一定要符合這個 schema
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "從這句話抽出商品資訊：「超好用自動鉛筆 0.5mm，特價 45 元，現貨供應，文具 學生 考試」"}],
    output_config={"format": {"type": "json_schema", "schema": schema}},
)

# 回覆的第一個文字區塊就是合法 JSON，直接用 json.loads 轉成 dict
text = next(b.text for b in response.content if b.type == "text")
data = json.loads(text)
print("型別：", type(data).__name__)
print("名稱：", data["name"])
print("價格：", data["price"], "元")
print("標籤：", data["tags"])
```

預期輸出：

```
型別： dict
名稱： 超好用自動鉛筆 0.5mm
價格： 45 元
標籤： ['文具', '學生', '考試']
```

注意 `price` 是整數 45，不是字串 `"45 元"`——因為 schema 說它是 `integer`。欄位的 `description` 很重要，它是模型決定「怎麼填」的依據。

### 用 pydantic 類別：更 Python 的寫法

手寫 JSON Schema 又長又容易打錯。**pydantic** 套件讓你用 Python 類別描述格式，SDK 的 `client.messages.parse()` 會自動轉成 schema 送出去，再把回覆變成物件：

```python
from pydantic import BaseModel, Field
import anthropic


# 用 pydantic 類別描述格式：欄位名稱、型別、說明，一目了然
class Product(BaseModel):
    name: str = Field(description="商品名稱")
    price: int = Field(description="價格，新台幣整數")
    in_stock: bool
    tags: list[str]


client = anthropic.Anthropic()

# parse() 會自動把類別轉成 schema 送出去，再把回覆轉回 Product 物件
response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "從這句話抽出商品資訊：「超好用自動鉛筆 0.5mm，特價 45 元，現貨供應，文具 學生 考試」"}],
    output_format=Product,
)

# parsed_output 已經是 Product 物件，可以直接用「點」取欄位
product = response.parsed_output
print(type(product).__name__, product)
print("價格乘以 10：", product.price * 10)
```

預期輸出：

```
Product name='超好用自動鉛筆 0.5mm' price=45 in_stock=True tags=['文具', '學生', '考試']
價格乘以 10： 450
```

`pip install pydantic`（裝 anthropic 時通常已經一起裝了）。這裡有個容易混淆的地方：`parse()` 的參數叫 `output_format=類別`，而 `create()` 用的是 `output_config={"format": ...}`。兩者底層一樣，只是 `parse()` 多幫你做了「類別 ↔ schema ↔ 物件」的轉換。本書之後需要 JSON 的地方一律用 `parse()`。

### 工具是什麼：模型沒有手

現在處理輸入問題。模型知道的只有訓練資料和你送進去的文字。它不知道今天的天氣、不會真的算 12345 × 6789（它會「猜」答案，常常猜錯）、不能讀你的檔案。

**工具（tool）**，也叫 **function calling（函式呼叫）**，是這樣運作的：

1. 你告訴模型「我有這幾個工具，各自是做什麼的、需要什麼參數」。
2. 模型回答時，如果覺得需要，就回一個 `tool_use` 區塊：「請幫我呼叫 `get_weather`，參數 `city="台北"`」。
3. **你的程式**真的去執行（查資料庫、呼叫天氣 API、算數學），把結果包成 `tool_result` 送回去。
4. 模型看到結果，繼續回答，或再要求下一個工具。

關鍵是第 3 步：**模型從頭到尾沒有碰到你的電腦**，它只會「說」想用什麼工具，執行的永遠是你的程式。這一點決定了安全邊界：模型說要刪檔案，你的程式可以拒絕。

```
 使用者 ──問題──▶ 模型 ──tool_use(get_weather, 台北)──▶ 你的程式
                   ▲                                      │
                   └────── tool_result("多雲 27°C") ◀──────┘ （真的去查）
                   │
                   └──▶ 「台北現在多雲 27 度」──▶ 使用者
```

### 定義一個工具

工具定義是一個 dict，三個欄位：`name`、`description`、`input_schema`（又是 JSON Schema）。`description` 是模型決定「什麼時候用這個工具」的唯一依據，要寫清楚。

```python
import json
import anthropic

client = anthropic.Anthropic()

# 工具定義：名字、說明（模型靠它決定何時用）、輸入格式
tools = [
    {
        "name": "get_weather",
        "description": "查詢某個城市現在的天氣。只有在使用者問到天氣時才使用。",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名稱，例如 台北"}},
            "required": ["city"],
        },
    }
]

# 把工具清單一起送出去；模型「不會」真的查天氣，它只會「要求」我們去查
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    tools=tools,
    messages=[{"role": "user", "content": "台北現在天氣怎麼樣？"}],
)

print("stop_reason：", response.stop_reason)
for block in response.content:
    if block.type == "tool_use":
        # 模型想呼叫工具：告訴你工具名、輸入參數、以及這次呼叫的 id
        print("模型想用工具：", block.name)
        print("輸入參數：", json.dumps(block.input, ensure_ascii=False))
        print("tool_use id：", block.id)
```

預期輸出：

```
stop_reason： tool_use
模型想用工具： get_weather
輸入參數： {"city": "台北"}
tool_use id： toolu_01AbCdEfGh
```

看到 `stop_reason` 是 `tool_use` 了嗎？模型停在這裡等你。`block.input` 已經是 dict，`block.id` 是這次呼叫的編號，等一下送結果回去時要對上。這個程式只做到「模型開口要工具」就結束；接下來要把迴圈補完。

### 工具迴圈：tool_use → 執行 → tool_result

完整的流程是一個 `while` 迴圈：只要 `stop_reason` 是 `tool_use`，就執行工具、把結果送回去、再問一次。結果的格式是 `{"type": "tool_result", "tool_use_id": 剛才的 id, "content": 結果字串}`，放在一則 `user` 訊息裡。

```python
"""手寫工具迴圈：模型說 tool_use 就執行工具，把結果送回去，直到它說完為止。"""
import ast
import json
import operator
import anthropic

client = anthropic.Anthropic()

# --- 工具本體：假天氣 + 安全的四則運算 ---
FAKE_WEATHER = {"台北": "多雲 27°C", "台中": "晴 30°C", "高雄": "雷陣雨 29°C"}


def get_weather(city: str) -> str:
    # 查不到就明確回報，不要亂編
    return FAKE_WEATHER.get(city, f"沒有 {city} 的資料")


OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv}


def safe_calc(expression: str) -> str:
    """只允許數字與 + - * / 的算式；用 ast 逐節點計算，不用 eval。"""
    def walk(node):
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            return OPS[type(node.op)](walk(node.left), walk(node.right))
        raise ValueError("只接受數字與 + - * /")
    return str(walk(ast.parse(expression, mode="eval").body))


# --- 工具定義（給模型看的說明書） ---
tools = [
    {"name": "get_weather", "description": "查某城市現在的天氣。",
     "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}},
    {"name": "calculate", "description": "計算四則運算算式，例如 12*34。",
     "input_schema": {"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]}},
]


def run_tool(name: str, args: dict) -> str:
    """依名字分派到真正的函式；任何例外都變成錯誤訊息回給模型。"""
    try:
        if name == "get_weather":
            return get_weather(str(args["city"]))
        if name == "calculate":
            return safe_calc(str(args["expression"]))
        return f"錯誤：沒有叫 {name} 的工具"
    except Exception as e:
        return f"錯誤：{e}"


messages = [{"role": "user", "content": "台北和高雄現在天氣如何？另外幫我算 12*34+5。"}]

while True:
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=2048, tools=tools, messages=messages,
    )
    # 模型講完了（沒有要用工具）就跳出迴圈
    if response.stop_reason != "tool_use":
        break

    # 先把模型這輪的回覆（含 tool_use 區塊）原封不動加進歷史
    messages.append({"role": "assistant", "content": response.content})

    # 執行每一個工具呼叫，結果全部放進「同一則」user 訊息送回去
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = run_tool(block.name, block.input)
            print(f"[工具] {block.name}({json.dumps(block.input, ensure_ascii=False)}) → {output}")
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
    messages.append({"role": "user", "content": results})

# 迴圈結束後，最後一個回覆就是給使用者的答案
print("[回答]", "".join(b.text for b in response.content if b.type == "text"))
```

預期輸出：

```
[工具] get_weather({"city": "台北"}) → 多雲 27°C
[工具] get_weather({"city": "高雄"}) → 雷陣雨 29°C
[工具] calculate({"expression": "12*34+5"}) → 413
[回答] 台北現在多雲 27°C，高雄有雷陣雨 29°C。12×34+5 = 413。
```

三個細節決定成敗。第一，`messages.append({"role": "assistant", "content": response.content})` 要放**整個** `content`，不能只放文字，因為 `tool_use` 區塊和 `thinking` 區塊都在裡面。第二，一次回覆可能有**好幾個** `tool_use`（這裡有三個），這叫**並行工具呼叫（parallel tool use）**；你要全部執行，結果放在**同一則** user 訊息裡送回去。拆成多則會讓模型以後不敢並行。第三，工具出錯不要讓程式炸掉，把錯誤當成結果回去（可以加 `"is_error": True`），模型會自己換個方式。

### tool_runner：讓 SDK 幫你跑迴圈

上面的迴圈每個專案都長一樣，SDK 提供 `@beta_tool` 裝飾器和 `client.beta.messages.tool_runner()` 幫你自動做：你只寫函式，型別提示和 docstring 會自動變成 `input_schema`。

```python
import json
import anthropic
from anthropic import beta_tool

FAKE_WEATHER = {"台北": "多雲 27°C", "高雄": "雷陣雨 29°C"}


# 裝飾器會讀函式的「參數型別」與「docstring」，自動產生工具定義
@beta_tool
def get_weather(city: str) -> str:
    """查詢某個城市現在的天氣。

    Args:
        city: 城市名稱，例如 台北。
    """
    return FAKE_WEATHER.get(city, f"查無 {city}")


# 印出來看：跟前面手寫的 name / description / input_schema 一模一樣
print(json.dumps(get_weather.to_dict(), ensure_ascii=False, indent=2))

client = anthropic.Anthropic()

# tool_runner 接手整個迴圈：呼叫 → 執行工具 → 送回結果 → 直到模型講完
runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=2048,
    tools=[get_weather],
    messages=[{"role": "user", "content": "台北天氣？"}],
)
final = runner.until_done()
print("".join(b.text for b in final.content if b.type == "text"))
```

預期輸出：

```
{
  "name": "get_weather",
  "description": "查詢某個城市現在的天氣。",
  "input_schema": {
    "additionalProperties": false,
    "properties": {
      "city": {"description": "城市名稱，例如 台北。", "title": "City", "type": "string"}
    },
    "required": ["city"],
    "type": "object"
  }
}
台北現在多雲 27°C。
```

`until_done()` 把整個迴圈跑完回傳最後一則訊息；想看每一輪可以 `for message in runner:`。活動 2-1 用的就是這個。`beta` 代表這個功能還在測試階段，介面可能微調，但本書驗證時可用。

### 安全：工具一定要驗證輸入

模型送來的 `input` 是**不可信的**。它可能打錯城市、可能被使用者的文字「騙」去做奇怪的事（這叫 **prompt injection，提示注入**，第 14 章會深談）。三條規則：

1. **不要用 `eval()`。** 「算數工具」最常見的錯誤寫法是 `eval(expression)`，只要模型送來 `__import__("os").system("rm -rf ~")`，你的家目錄就沒了。上面的 `safe_calc` 用 `ast` 只允許數字與四則運算。
2. **檢查型別與範圍。** schema 說是 `string` 不代表內容安全；檔案路徑要確認在允許的資料夾內，數字要確認在合理範圍。
3. **最小權限。** 工具能做的事越少越好。「讀檔」不要順便能「寫檔」；「查資料庫」用唯讀帳號。

把工具定義加上 `"strict": True`（schema 要有 `additionalProperties: false` 和 `required`）可以保證模型送來的參數完全符合 schema，少掉一層型別檢查，但內容的安全還是要你自己把關。

## 動手做

### 活動 2-1：會查天氣（假資料）與算數的小助理

**材料／工具**：venv、`anthropic` 與 `pydantic`、金鑰。

**步驟**：

1. 建立 `assistant.py`，貼入程式，執行 `python assistant.py`。
2. 觀察三個問題各呼叫了哪些工具：天氣問題應該呼叫 `get_weather` 兩次（並行），算數問題呼叫 `calculate`，鼓勵的話**不該**呼叫任何工具。
3. 把 `FAKE_WEATHER` 加一個你家的城市，問它你家的天氣。
4. 問一個沒有的城市（例如「東京」），看工具怎麼回報、模型怎麼轉述。
5. 試著問「幫我算 2 的 100 次方」，看 `calculate` 拒絕 `**` 之後模型怎麼辦。
6. 挑戰：加一個 `get_time()` 工具回傳現在時間（用 `datetime`），問「現在幾點」。

```python
"""活動 2-1：會查天氣（假資料）與算數的小助理，用 tool_runner 自動跑工具迴圈。"""
import ast
import operator
import anthropic
from anthropic import beta_tool

FAKE_WEATHER = {"台北": "多雲 27°C，降雨機率 40%", "台中": "晴 30°C", "高雄": "雷陣雨 29°C", "花蓮": "陰 25°C"}
OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv}


# @beta_tool 會從「型別提示 + docstring」自動做出工具說明書，不用手寫 JSON Schema
@beta_tool
def get_weather(city: str) -> str:
    """查詢台灣某個城市現在的天氣（示範用假資料）。

    Args:
        city: 城市名稱，例如 台北、高雄。
    """
    # 查不到要老實說，模型才不會亂編
    return FAKE_WEATHER.get(city.strip(), f"查無 {city} 的天氣資料")


@beta_tool
def calculate(expression: str) -> str:
    """計算只含數字與 + - * / 和括號的算式，例如 (12+3)*4。

    Args:
        expression: 要計算的算式字串。
    """
    # 用 ast 逐節點計算，絕對不用 eval（eval 會執行任何程式碼，很危險）
    def walk(node):
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            return OPS[type(node.op)](walk(node.left), walk(node.right))
        raise ValueError("只接受數字與 + - * /")
    try:
        return str(walk(ast.parse(expression, mode="eval").body))
    except Exception as e:
        return f"計算失敗：{e}"


client = anthropic.Anthropic()


def ask(question: str) -> str:
    """把問題交給 tool_runner，它會自動：呼叫模型 → 跑工具 → 送回結果 → 直到模型答完。"""
    runner = client.beta.messages.tool_runner(
        model="claude-opus-5-5",
        max_tokens=2048,
        system="你是小助理。需要天氣或算數時一定用工具，不要自己猜；回答用繁體中文。",
        tools=[get_weather, calculate],
        messages=[{"role": "user", "content": question}],
        max_iterations=5,  # 最多來回 5 次，避免失控
    )
    # 每一輪模型回覆都會經過這裡，順便印出它呼叫了哪些工具
    for message in runner:
        for block in message.content:
            if block.type == "tool_use":
                print(f"   [工具呼叫] {block.name} {block.input}")
    # until_done() 回傳最後一則訊息
    final = runner.until_done()
    return "".join(b.text for b in final.content if b.type == "text")


if __name__ == "__main__":
    for q in ["台北和花蓮現在天氣如何？", "幫我算 (12+3)*4 再除以 5", "今天心情不錯，給我一句鼓勵的話"]:
        print("你>", q)
        print("AI>", ask(q))
        print()
```

### 活動 2-2：把摘要工具改成輸出 JSON

**材料／工具**：同上，加第 1 章的 `article.txt`。

**步驟**：

1. 建立 `summarize_json.py`，貼入程式。
2. 執行 `python summarize_json.py article.txt`，確認印出標題、三句、關鍵字、閱讀時間，並產生 `summary.json`。
3. 用文字編輯器打開 `summary.json`，確認它是合法 JSON（可以貼到任何 JSON 檢查網站）。
4. 在 `Summary` 類別加一個欄位 `tone: str = Field(description="文章語氣：中立、正面或負面")`，再跑一次，看它多填了什麼。
5. 把 `sentences` 的說明改成「剛好五句」，看程式的警告有沒有出現。
6. 挑戰：改成讀取資料夾裡所有 `.txt`，把每篇的結果存成一個 list 寫進 `summaries.json`。

```python
"""活動 2-2：摘要工具 JSON 版。用法：python summarize_json.py 文章.txt"""
import json
import sys
from pydantic import BaseModel, Field
import anthropic

MODEL = "claude-opus-5-5"


# 先用 pydantic 把「摘要長什麼樣」定義清楚
class Summary(BaseModel):
    title: str = Field(description="幫文章取一個 15 字以內的標題")
    sentences: list[str] = Field(description="剛好三句摘要：主題、重點細節、結論")
    keywords: list[str] = Field(description="3 到 5 個關鍵字")
    reading_minutes: int = Field(description="一般人讀完原文大約需要幾分鐘")


client = anthropic.Anthropic()


def summarize(article: str) -> Summary:
    response = client.messages.parse(
        model=MODEL,
        max_tokens=1024,
        system="你是摘要助手，用繁體中文，依指定格式輸出。",
        messages=[{"role": "user", "content": f"文章如下：\n\n{article}"}],
        output_format=Summary,
    )
    return response.parsed_output


def main():
    if len(sys.argv) < 2:
        print("用法：python summarize_json.py 文章.txt")
        sys.exit(1)
    with open(sys.argv[1], encoding="utf-8") as f:
        article = f.read().strip()

    summary = summarize(article)

    # 因為是物件，可以直接檢查：是不是剛好三句？不是就警告
    if len(summary.sentences) != 3:
        print(f"警告：模型給了 {len(summary.sentences)} 句，不是 3 句")

    print("標題：", summary.title)
    for i, s in enumerate(summary.sentences, 1):
        print(f"  {i}. {s}")
    print("關鍵字：", "、".join(summary.keywords))
    print("閱讀時間：約", summary.reading_minutes, "分鐘")

    # 存成 JSON 檔，給其他程式（或試算表）用
    with open("summary.json", "w", encoding="utf-8") as f:
        json.dump(summary.model_dump(), f, ensure_ascii=False, indent=2)
    print("已存成 summary.json")


if __name__ == "__main__":
    main()
```

```

  1. 夜市是從日治時期廟口小吃攤發展而來的台灣庶民文化。
  2. 1980 年代後夜市加入套圈圈、撈金魚等遊戲，成為許多人的童年回憶。
  3. 如今全台有三百多個夜市吸引觀光客，但也面臨垃圾、噪音與食安挑戰。
關鍵字： 夜市、庶民文化、觀光、食安
閱讀時間：約 1 分鐘
已存成 summary.json
```

## 程式與執行：看一次完整的工具迴圈

核心概念裡的 `manual_loop.py` 就是本章的「完整程式」。這裡說明怎麼跑、怎麼看。

**怎麼跑**：把「工具迴圈」那段存成 `manual_loop.py`，`python manual_loop.py`。

**輸出怎麼讀**：每一行 `[工具]` 代表模型開口要了一次工具、你的程式執行了一次。把迴圈每一輪送出去的 `messages` 畫出來：

```
第 1 輪送出：[user: 問題]
       收到：assistant: [tool_use ×3]            stop_reason = tool_use
第 2 輪送出：[user: 問題, assistant: [tool_use ×3], user: [tool_result ×3]]
       收到：assistant: [text: 最終回答]          stop_reason = end_turn → 跳出
```

想看得更清楚，在 `while` 迴圈最上面加一行 `print(len(messages), "則訊息")`，你會看到 1、3。如果模型要求的工具不止一輪（例如先查天氣再依天氣算東西），會看到 1、3、5。

**跟 tool_runner 的差別**：`assistant.py` 做的事完全一樣，只是迴圈在 SDK 裡。要自己寫還是用 runner？規則是：**想完全掌控每一步（例如每次執行工具前問使用者要不要允許）就自己寫，否則用 runner**。其實 runner 也能做到允許確認——在 `for message in runner:` 裡檢查 `tool_use` 區塊，不想執行就讓工具函式回傳「使用者拒絕」。第 5 章的 agent 會再用到。

## 常見錯誤與迷思

- **「我請它回 JSON，它回了 ```json 包起來的字串，json.loads 失敗」** → 這是只靠提示要求格式的老問題。 → 用 `output_config` 或 `parse()`，API 保證回合法 JSON，不會有多餘的包裝。
- **「parse() 我寫 output_config=Summary 報錯」** → `parse()` 的參數是 `output_format=類別`；`create()` 才是 `output_config={"format": ...}`。 → 記住：類別給 `output_format`，schema dict 給 `output_config`。
- **「模型呼叫了工具，但我沒把結果送回去，它就一直要求同一個工具」** → 它在等 `tool_result`。 → 每個 `tool_use` 都要有對應 `tool_use_id` 的 `tool_result`，缺一個 API 就會報 400。
- **「我把 assistant 的回覆只存文字，下一輪報錯」** → `tool_use` 區塊不見了，`tool_result` 對不上。 → `messages.append({"role": "assistant", "content": response.content})` 放整個 content。
- **「我用 eval 算數學很方便」** → 模型（或透過模型的使用者）送來的字串可以是任何 Python 程式碼。 → 用 `ast` 白名單，或用專門的算式套件。
- **「我想強迫它一定用某個工具，設 tool_choice={"type": "any"}」** → `claude-opus-5-5` 不支援強迫，會回 400。 → 在 system 或問題裡明說「請用 get_weather 工具」，並在工具加 `strict: True`；真的只是要 JSON 的話用結構化輸出。
- **「工具的 description 寫『天氣』兩個字就好」** → 模型只靠 description 判斷何時用、怎麼填參數，太短會誤用或不用。 → 寫清楚做什麼、什麼時候用、參數格式與例子。
- **「工具結果裡的文字模型一定會照做」** → 工具結果可能來自網頁或檔案，裡面可能藏著「忽略之前的指示」這類文字。 → 把工具結果當資料不當指令；敏感操作要人確認。

## 想一想

1. 結構化輸出和「在提示裡寫『請回 JSON』」差在哪裡？為什麼前者比較可靠？

<details><summary>參考答案</summary>

提示只是「請求」，模型可能多講一句、換個格式、漏欄位；結構化輸出是 API 層的「保證」，回覆一定符合你給的 schema，程式可以直接 `json.loads` 或拿到物件，不用猜。

</details>

2. 模型回了 `tool_use` 要呼叫 `delete_file(path="/")`。這時候檔案被刪了嗎？誰決定要不要刪？

<details><summary>參考答案</summary>

還沒。模型只是「要求」，真正執行的是你的程式。你的 `run_tool` 可以檢查路徑、拒絕、或問使用者。這就是工具設計的安全邊界：永遠由程式決定做不做。

</details>

3. 一次回覆裡有三個 `tool_use`，你把三個 `tool_result` 分成三則 user 訊息送回去。會怎樣？

<details><summary>參考答案</summary>

API 會把連續的 user 訊息合併，所以不一定報錯，但這樣的歷史會讓模型學到「一次只能用一個工具」而不再並行，之後變慢、變貴。正確做法是三個結果放在同一則 user 訊息的 content list 裡，而且每個都要有對應的 `tool_use_id`。

</details>

3b. （延伸）如果三個結果裡有一個工具執行失敗了，該怎麼回？

<details><summary>參考答案</summary>

還是要回三個 `tool_result`，失敗的那個把 `content` 寫成錯誤訊息並加 `"is_error": True`。千萬不要省略它，少一個 `tool_result` API 會報 400。

</details>

4. 把 `calculate` 的 schema 加上 `"strict": True`，就不用檢查輸入了嗎？

<details><summary>參考答案</summary>

不是。strict 只保證「型別與欄位」符合 schema（`expression` 一定是字串），不保證「內容」安全。字串裡還是可以是惡意程式碼，所以 `safe_calc` 的 ast 白名單仍然必要。

</details>

5. 為什麼活動 2-1 的 `get_weather` 查不到城市時回「查無資料」，而不是回空字串或丟例外？

<details><summary>參考答案</summary>

空字串模型可能誤以為是「沒有天氣」而亂編；丟例外會讓整個程式中斷。明確的錯誤訊息讓模型知道發生了什麼，它會轉述給使用者或換個城市名再試。

</details>

6. 開放挑戰：設計一個「家庭採買助理」，工具有 `list_inventory()`（回家裡現有的食材，假資料）、`add_to_cart(item, qty)`、`get_price(item)`。使用者說「晚餐想煮咖哩，幫我列出要買的東西和預算」。畫出模型可能的工具呼叫順序，哪些可以並行、哪些必須等前一步？

<details><summary>參考答案</summary>

可能順序：(1) `list_inventory()` 先看有什麼（必須先做）；(2) 對每樣缺的食材並行呼叫 `get_price()`；(3) 並行 `add_to_cart()` 每樣；(4) 回答清單與總預算。第 2、3 步依賴第 1 步的結果，所以會是三輪迴圈。安全上 `add_to_cart` 是「會花錢」的動作，建議在工具裡印出確認或先回傳「待確認清單」讓使用者點頭再真的加。

</details>

## 本章小結

- 程式需要固定格式，不是自然語言；結構化輸出讓 API 保證回合法 JSON。
- `create()` 用 `output_config={"format": {"type": "json_schema", "schema": ...}}`；`parse()` 用 `output_format=pydantic類別`，回來的 `parsed_output` 直接是物件。
- 工具讓模型「要求」你的程式做事；模型從不直接碰你的電腦，執行與否由程式決定。
- 工具定義三件事：`name`、`description`（決定何時用）、`input_schema`。
- 迴圈：`stop_reason == "tool_use"` → 把整個 `response.content` 存回歷史 → 執行每個工具 → 所有 `tool_result` 放同一則 user 訊息 → 再呼叫，直到 `end_turn`。
- `@beta_tool` + `tool_runner().until_done()` 幫你自動跑這個迴圈。
- 工具輸入不可信：不用 `eval`、檢查型別與範圍、最小權限；工具結果當資料不當指令。
- `claude-opus-5-5` 不支援強迫工具（`tool_choice: any`），用提示與 `strict` 代替。
